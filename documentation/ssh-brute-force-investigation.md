# SSH Brute-Force Detection and Automated Response

## 1. Overview

This project demonstrates the detection, investigation, and response to repeated SSH authentication failures in a controlled cybersecurity home lab.

Kali Linux was used to simulate SSH password-guessing activity against an Ubuntu Linux endpoint. Wazuh monitored the endpoint's security events, correlated matching authentication events using a custom detection rule, and initiated an automated response through Wazuh Active Response.

The investigation documents the attack simulation, endpoint evidence, SIEM detection, and response validation.

## 2. Objectives

* Simulate SSH password-guessing activity in an isolated lab environment.
* Monitor authentication events generated on the Ubuntu endpoint.
* Detect repeated authentication failures using a custom Wazuh correlation rule.
* Investigate the resulting alert using endpoint logs and SIEM evidence.
* Map the observed behavior to MITRE ATT&CK.
* Evaluate the configured automated response and document its outcome.

## 6. Wazuh Detection Logic

A custom Wazuh correlation rule was created to detect repeated SSH authentication failures associated with the same source IP address.

### Rule Configuration

| Property           | Value                     |
| ------------------ | ------------------------- |
| Rule ID            | 127000                    |
| Alert Level        | 12                        |
| Frequency          | 3                         |
| Timeframe          | 120 seconds               |
| Source Correlation | Same source IP            |
| Detection Category | SSH brute-force detection |

The rule uses previously matched authentication events and source-IP correlation to identify repeated activity within the configured timeframe.

The complete rule is available at:

## 7. MITRE ATT&CK Mapping

The observed behavior is relevant to the following MITRE ATT&CK technique:

* **Tactic:** Credential Access
* **Technique:** T1110 — Brute Force
* **Potential Sub-technique:** T1110.001 — Password Guessing

T1110.001 is appropriate when the simulated activity involves repeated attempts to guess a password. The mapping should reflect the actual behavior demonstrated by the lab.

Reference: [MITRE ATT&CK — Brute Force (T1110)](https://attack.mitre.org/techniques/T1110/)

## 8. Investigation and Assessment

The investigation follows a correlation-based approach:

1. Review the attack simulation details from Kali Linux.
2. Examine the Ubuntu authentication logs for corresponding SSH events.
3. Compare event timestamps and source IP addresses.
4. Review the Wazuh alerts associated with the activity.
5. Verify whether custom rule 127000 triggered.
6. Examine the configured response and available evidence of its execution.
7. Record the findings and any limitations.

### Assessment

Repeated SSH authentication failures from the same source can be consistent with password-guessing activity.

A final classification should be based on the available endpoint logs, Wazuh alerts, and attack-simulation evidence.

The investigation does not, by itself, establish that an account was compromised.

## 9. Automated Response

Wazuh Active Response was configured to use the `firewall-drop` command when rule 127000 triggers.

The configured response parameters include:

* Response command: `firewall-drop`
* Response location: `local`
* Triggering rule: `127000`
* Configured timeout: 300 seconds
* Repeated-offender intervals: 60, 300, and 900 seconds

These settings describe the configured response behavior. Actual execution and blocking must be evaluated using the corresponding evidence.

## 10. Validation and Limitations

The investigation uses multiple evidence sources to evaluate the detection and response workflow.

### Validation Points

* Confirm that the Ubuntu endpoint recorded the relevant authentication events.
* Correlate the authentication events with the Wazuh alerts.
* Verify that custom rule 127000 triggered as intended.
* Confirm that the active-response configuration references the expected rule.
* Verify blocking and recovery using appropriate network or firewall evidence.

### Limitations

* A detection alert does not establish that authentication was successful.
* Repeated failed logins can have legitimate causes and require investigation.
* Source-IP correlation depends on the accuracy and availability of event fields.
* A failed ping alone is insufficient to prove firewall enforcement.
* The effectiveness of the detection depends on the underlying rules, log collection, and correlation behavior.
* Findings are limited to the evidence collected in this lab environment.

## 11. Lessons Learned

This exercise demonstrates the importance of correlating endpoint telemetry with SIEM alerts rather than relying on a single security event.

It also highlights the need to validate detection logic, investigate potential false positives, and distinguish between configured automated responses and responses whose execution has been verified.

A defensible SOC investigation should connect the original activity, endpoint evidence, detection result, analyst assessment, and response outcome.
